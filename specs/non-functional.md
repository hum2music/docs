# Non-Functional Requirements Spec（完成系）

対応：PRD §15。全フェーズを通して守るべき非機能要件を一箇所に集約する。

## 再現性（PRD §15.1）

- 同じ入力音声・設定（CLIオプション/UI設定）・`seed`・エンジンバージョンに対して、常に同一のMIDIイベント列を生成すること
- `Composition.metadata`にエンジンバージョン（各パッケージのバージョンまたはアルゴリズムIDの組）を記録し、異なるバージョン間での差異を区別可能にする（[data-model.md](./data-model.md)）
- 確率的処理はすべて`seed`から決定的に導出したサブシードを使う（[expression.md](./expression.md)）。`Math.random()`等、seedに依存しない乱数源の直接利用を全パッケージで禁止する
- 完成系の受け入れテスト：同一入力に対して複数回実行したMIDIバイト列（またはNoteEvent列のハッシュ）が完全一致することを自動テストで検証する

## パフォーマンス（PRD §15.2）

- 初期目標：30秒の単旋律WAVを一般的な開発用PCで10秒以内に解析・編曲完了（UIレンダリング時間は除外）
- 完成系（Phase 5まで、ギター・複数スタイル・WAVレンダリング込み）でも、この目標を大きく超えないことを継続的にベンチマークする
- 各エンジン単位でのプロファイリングを可能にし、パイプライン全体のボトルネックを特定できるようにする（[architecture.md](./architecture.md)のモジュール分離が前提）
- 実装初期にベンチマークを取得し、必要に応じて目標値を見直す（固定値として最初から厳密運用しない）

## オフライン対応（PRD §15.3）

- 音響解析・楽曲生成・MIDI出力は完全オフラインで動作することを維持する
- WAVレンダリング（Phase 5）で使用するローカル音源/シンセサイザーも、外部APIやオンラインサービスに依存しないものを選定する（[export.md](./export.md)）
- localhost UI（Phase 4）も、外部CDN等への依存を避け、バンドルされたアセットのみで動作することを前提とする

## テスト容易性（PRD §15.4）

- 各エンジン（audio-analysis, music-theory, harmony, arrangement/*, expression, midi, rendering）を独立してテストできること
- 各工程が中間データをJSONで出力できること（デバッグ・比較のため）
- 完成系では、Phase 0〜5で追加される機能（スタイルプロファイル、UIバックエンドAPI、WAVレンダリング）についても、対応するFixtureと自動テストを備えること

## エラー処理（PRD §15.5）

以下の状況を検出した場合、原因と利用可能な代替操作をユーザーに提示する。不確かな値を確定値として扱わない。

- 音声ファイルの破損
- 対応外のフォーマット
- 有効な音高が検出できない
- テンポが推定できない
- コード進行の信頼度が低い

完成系では、上記に加えて以下も同じ方針（原因提示＋代替操作の提示、確定値への強制fallback禁止）でカバーする：

- スタイルプロファイルが未知/存在しない指定（`--style`に不正な値）
- WAVレンダリング用のローカル音源が見つからない
- localhost UIでのマイク録音許可拒否・デバイス取得失敗

## 品質評価（PRD §16、完成系での扱い）

- 音響解析：Pitch Accuracy / Note Onset Error / Note Duration Error / Tempo Estimation Error
- 編曲：コードとメロディーの適合性 / 楽器の演奏可能性 / メロディーの保持率 / 音楽的一貫性
- 主観評価：自然さ / 心地よさ / 鼻歌の意図が残っているか / 人間らしい表現があるか
- 主観評価は単一の正解が存在するものとして扱わない（PRD §16.3）。完成系でも、数値化した評価指標を「唯一の正解」として自動判定に使わず、人間によるレビューと併用する
